# AGENTS.md

Guidance for AI coding agents working in this repository. Read
[CONTRIBUTING.md](CONTRIBUTING.md) and [tests/resources/README.md](tests/resources/README.md)
for the full workflow.

## Overview

`terraform-provider-konnect` is the Terraform provider for Kong Konnect
(`registry.terraform.io/providers/Kong/konnect`). It is written in Go with the
Terraform Plugin Framework, and **most of it is generated by Speakeasy** from
`openapi.yaml`.

## Generated vs hand-written code

Do not hand-edit generated files. The next `make speakeasy` overwrites your change.

| Path | Status |
|---|---|
| `openapi.yaml` | Generated from Kong's private `platform-api` repo. Direct edits are lost. Raise an issue for spec changes. |
| `internal/sdk/**` | Generated. |
| `internal/provider/*_resource.go`, `*_resource_sdk.go`, `internal/provider/types/**`, `provider.go` | Generated (`// Code generated by Speakeasy ... DO NOT EDIT.`). |
| `docs/**` | Generated by `tfplugindocs` (`go generate`). The example blocks in the docs are Speakeasy placeholders. |
| `.speakeasy/gen.lock` | Generated. A change to it on `main` triggers a release. |
| `examples/resources/*.tf` | **Hand-written.** `make speakeasy` runs `git clean -fd examples`, so generated examples are discarded. |
| `CHANGELOG.md`, `tests/**`, `CONTRIBUTING.md`, `scripts/`, `.github/` | Hand-written. |

If a generated schema or description is wrong, the fix belongs in the OpenAPI spec or
the Speakeasy configuration, not in the generated Go file.

## Commands

```sh
make speakeasy                          # regenerate the provider (needs the speakeasy CLI)
go build ./...                          # build
export KONNECT_SPAT=...                 # token for acceptance tests
make acceptance-shard SHARD=gateway     # run one acceptance shard
make acceptance                         # run every shard
make check-shards                       # check the test layout; needs no credentials
TF_ACC=1 go test -v -run TestName ./tests/resources/gateway   # one acceptance test (needs KONNECT_SPAT)
go test ./internal/...                  # unit tests, no credentials
```

`make test` is not the acceptance suite. It is an end-to-end run in `tests/e2e` against a
specific maintainer-owned org, and others cannot run it yet. Do not run it, and do not use it
to verify a change.

Acceptance tests create real resources in a real Konnect org. Do not run them against
an org you were not told to use, and do not print or write tokens to files in the repo.

## Acceptance tests

Tests live in `tests/resources/<shard>/`, one directory per product area
(`gateway`, `aigateway`, `eventgateway`, `portalapi`, `identityorg`, and so on). Each
shard is one parallel CI job.

- Put a new test in the shard for its product area. Never put `*_test.go` files directly in
  `tests/resources/`. `make check-shards` fails if you do.
- A new area needs a new directory with a `provider_test.go` (copy an existing one) and an
  entry in the matrix in `.github/workflows/provider-tests.yaml`.
- Name the file `{resource}_test.go`. Config files go in
  `tests/resources/<shard>/testdata/{TestName}/`.
- Test function names must be unique across all shards.
- A shard must pass on its own. Do not read a resource that another shard creates.
- Org quotas are shared by every shard and every concurrent run (for example 4 portals).
  Keep tests for limited resources in the shard that already owns them.
- Use the shared provider setup in `tests/internal/acc`.
- Unit tests sit next to the code they test (for example `internal/validators`). Add one for
  hand-written logic. Do not unit test generated code.

### Features behind a flag, and long-running resources

If a resource depends on an org feature flag, or is too slow for CI, still write the test
and call `t.Skip` with a one-line reason, as `gateway_plugin_ace_test.go` and
`cloud_gateway_network_test.go` do. Run it manually against a suitable org before merging
and say so in the PR. Do not skip a test just because it is hard to write.

### Scope of the update-test rule

The rule below applies to resources a PR adds or changes. Do not add update tests to
untouched resources as part of an unrelated change. Many existing tests only cover create,
and filling those gaps is separate work.

### Every resource must have an update test

A PR that adds a resource, or changes a resource's schema, must include an acceptance
test that **updates** the resource, not only creates it and checks for an empty re-plan.

The test must:

1. Create the resource.
2. Change at least one configurable attribute in a later step and apply it.
3. Assert the plan action with `plancheck.ExpectResourceAction`:
   - `ResourceActionUpdate` for attributes that update in place.
   - `ResourceActionDestroyBeforeCreate` or `ResourceActionReplace` for attributes marked
     `RequiresReplace`.
4. Assert the new value in state, then finish with `plancheck.ExpectEmptyPlan()` to prove
   there is no drift.

Also cover these cases when they apply:

- **Every changeable attribute.** An attribute that forces replacement must be tested as a
  replacement. If the API has an update endpoint but a field cannot be updated in place,
  say why in a comment on the test.
- **Identifier or path attributes** (for example an `event_type` used in a URL path).
  Changing one must force replacement, because the update call cannot move the object.
- **Dependent resources.** If replacing or deleting resource A changes or deletes resource
  B on the server (for example, deleting a destination deletes a subscription left with no
  destinations), test the pair through an update of A.
- **Import.** Add an `ImportState` step with `ImportStateVerify`. List attributes the API
  does not return (secrets, header values) under `ImportStateVerifyIgnore`. Verify that a
  plan after import shows no changes.

A resource with no update test is not ready to merge.

## Sensitive values

Mark attributes that hold secrets (signing secrets, tokens, passwords, credential and header
values) as `Sensitive`. Run `terraform show` against a real apply and confirm the value is not
printed in plaintext. Because the schema is generated, a missing `Sensitive` flag is fixed in the
OpenAPI spec or Speakeasy configuration.

## Examples and changelog

- Add an example for every new resource in `examples/resources/{resource}.tf`. Use realistic
  names, references to other resources (`konnect_x.example.id`) and real enum values, not
  Speakeasy placeholders.
- Add an entry to `CHANGELOG.md` under the release being prepared. Say what the user can do,
  following the existing entries ("Add support for `konnect_x` resource, using which you can
  ..."), and mention any condition the feature needs, such as a feature flag.
- Keep the release date as `Released 2026/??` until the release branch is merged.

## Branches, commits and PRs

- PRs target the release branch `release/x.y.z`, not `main`. Merging it to `main` releases
  the provider.
- Preferred commit split: (1) OpenAPI changes, (2) provider changes including `.speakeasy`
  and `docs`, (3) examples, (4) changelog.
- Use `.github/PULL_REQUEST_TEMPLATE.md`. List related `platform-api` PRs.

## Boundaries

### Ask first
- Changes to `.github/workflows/`, other than adding a shard to the acceptance matrix.
- Changes to `Makefile` or `scripts/`.
- Adding Go dependencies.

### Never
- Hand-edit generated files listed above.
- Run tests or Terraform against an org you were not given, or leave resources behind.
  Destroy what you create.
- Commit tokens or `KONNECT_*` values, or write them into files in the repo.
